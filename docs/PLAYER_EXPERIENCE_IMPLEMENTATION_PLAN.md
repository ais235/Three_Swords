# Three Blades — план улучшения игрового опыта

Статус документа: **канонический план следующих изменений**.  
Дата фиксации: **2026-07-23**.  
Основание: игровой аудит текущей сборки, существующий `UX_GAMEPLAY_OVERHAUL_PLAN.md`, отчёт по балансу и текущие автоматические проверки.

## 1. Назначение документа

Этот файл определяет порядок дальнейшей работы над игрой. Его задача — превратить уже существующий богатый тактический прототип в понятную, быструю и эмоционально выразительную игру для ПК и мобильных устройств.

Главный продуктовый вывод:

> Игре не требуется срочно больше контента. Сначала необходимо быстрее показывать глубину уже существующих систем, убрать пустые действия, улучшить читаемость и усилить награду за решения игрока.

Поддерживаемые форматы игры:

- ПК в альбомном формате;
- мобильные устройства только в альбомной ориентации;
- портретный игровой интерфейс не входит в область разработки;
- в портретной ориентации игра показывает только полноэкранную просьбу повернуть устройство и сохраняет текущее состояние.

При конфликте с `docs/UX_GAMEPLAY_OVERHAUL_PLAN.md`:

- этот документ имеет приоритет для новых изменений игрового опыта;
- старый план остаётся источником истории проекта, платформенных ограничений и выполненных работ;
- архитектурный рефакторинг и релизная упаковка выполняются только после стабилизации основных игровых экранов.

## 2. Рабочие правила

### 2.1. Обозначения статуса

- `[ ]` — не начато;
- `[~]` — выполняется;
- `[x]` — выполнено и проверено;
- `[!]` — заблокировано или требует отдельного решения.

### 2.2. Правила реализации

1. Выполнять задачи строго по приоритету и зависимостям из этого документа.
2. Один рабочий блок должен решать одну пользовательскую проблему.
3. Не добавлять новых врагов, регионов и больших мета-систем, пока не завершены этапы P0–P3.
4. Любое изменение баланса должно проверяться фиксированными seed и фиксироваться в `docs/BALANCE_SEED_REPORT.md`.
5. Все новые строки интерфейса добавлять через существующую систему локализации RU/EN/ES.
6. Не ломать старые сохранения. При изменении структуры данных добавлять безопасные значения по умолчанию или миграцию.
7. Не использовать боевой лог как единственный канал важной информации.
8. Новая механика считается готовой только тогда, когда игрок видит её причину и результат непосредственно в интерфейсе.
9. Мобильный альбомный режим проверять одновременно с desktop-версией, а не после неё.
10. Не начинать большой перенос кода из `index.html`, пока не закреплены новые правила экранов и игрового цикла.

## 3. Целевой игровой опыт

### 3.1. Первые пять минут

Игрок должен:

1. Понять роли Гарета, Алиры и Сэрис.
2. Использовать минимум одно характерное умение каждого героя.
3. Сделать первый содержательный выбор позиции не позднее второго хода героя.
4. Завершить первый бой без длинной серии пустых перемещений.
5. Получить заметную награду и увидеть направление развития отряда.
6. Понять, куда идти дальше и чем отличаются доступные маршруты.

Целевые ориентиры:

- первый содержательный ввод в бою — не позднее 20 секунд после расстановки;
- первое доступное активное умение — с первого хода;
- первый контакт с противником — в первом раунде;
- длительность первой обучающей битвы — ориентировочно 3–5 минут;
- после победы у игрока появляется хотя бы один новый предмет или другой гарантированный источник силы.

### 3.2. Обычный боевой ход

За несколько секунд игрок должен понимать:

- кто сейчас ходит;
- куда можно переместиться;
- кого можно атаковать;
- сколько приблизительно урона получит цель;
- что блокирует атаку;
- какая цель наиболее опасна;
- можно ли применить умение;
- что произойдёт после подтверждения действия.

### 3.3. Цикл кампании

Целевой цикл:

> Выбор маршрута → понятная угроза → тактический бой → яркая награда → заметное усиление → новый осмысленный выбор.

Каждая часть цикла должна готовить следующую:

- карта объясняет риск и возможную награду;
- бой проверяет собранный билд;
- победа показывает рост силы;
- инвентарь и перки меняют следующие решения;
- новый маршрут предлагает другой тип риска.

## 4. Приоритеты

| Приоритет | Содержание | Причина |
|---|---|---|
| P0 | Первый бой и доступность базовых умений | Сейчас первые ходы не показывают сильные стороны игры |
| P0 | Мобильная читаемость и блокировка портретной ориентации | Игра поддерживает только landscape; в portrait требуется экран поворота |
| P1 | Темп, управление и боевая отдача | Правильные решения ощущаются слабее, чем должны |
| P1 | Понятный выбор маршрута | Карта показывает масштаб, но слабо формирует решение |
| P2 | Билды, перки, предметы и победный экран | Рост существует математически, но недостаточно эмоционален |
| P2 | Кривая сложности и генератор встреч | Между регионами и отдельными встречами есть резкие скачки |
| P3 | Цели, повествование и удержание | Добавлять после укрепления основного цикла |
| P4 | Архитектура, производительность и релиз | Выполнять после стабилизации UX |

## 5. Этап A — первые минуты и первый бой

Цель: в первой миссии сразу показать тактическую индивидуальность всех трёх героев.

### A1. Стартовые умения

- [ ] Открыть с первого уровня:
  - Гарет — `Shield Bash`;
  - Алира — `Double Shot`;
  - Сэрис — `Fireball`.
- [ ] Оставить следующие умения этапами роста, ориентировочно на уровнях 3 и 5.
- [ ] Проверить стоимость, урон и перезарядку стартовых умений отдельно для первого региона.
- [ ] Заменить три визуально заблокированных слота на схему:
  - доступное основное умение;
  - ближайшее будущее умение с понятным уровнем открытия;
  - дальняя цель развития.
- [ ] Обновить обучение, описания героев, экран прокачки и экран открытия умений.
- [ ] Обеспечить совместимость существующих сохранений.

### A2. Специальный сценарий первой миссии

- [ ] Выделить первую миссию в отдельный предсказуемый encounter, не зависящий от обычной генерации волн.
- [ ] Использовать не более трёх врагов с простыми ролями:
  - ближний противник для Гарета;
  - уязвимая дальняя или приоритетная цель для Алиры;
  - небольшая группа или соседние цели для Fireball Сэрис.
- [ ] Разместить стороны так, чтобы контакт произошёл в первом раунде.
- [ ] Убрать из первой миссии тяжёлые сочетания контроля, лечения, призыва и взрывов.
- [ ] Оставить одно очевидное препятствие или укрытие, которое обучает позиции, но не блокирует начало боя.
- [ ] Сохранить возможность ручной расстановки, но предложить корректную автоматическую расстановку.

### A3. Контекстное обучение вместо текстового блока

- [ ] Сократить вводное обучение до цели кампании, ролей героев и сохранения.
- [ ] Обучать действиям во время первой миссии:
  - выбрать Гарета;
  - переместить его на защитную позицию;
  - применить `Shield Bash`;
  - выбрать цель Алиры;
  - показать смысл дальности;
  - применить `Fireball` по нескольким клеткам.
- [ ] Каждая подсказка должна подсвечивать конкретный элемент и исчезать после правильного действия.
- [ ] Игрок всегда может пропустить подсказку.
- [ ] После пропуска игра не должна блокировать обычные действия.

### A4. Первая победа

- [ ] Гарантировать первый предмет, который подходит одному из героев.
- [ ] Показать сравнение предмета с пустым или текущим слотом.
- [ ] Дать игроку понятный следующий шаг: открыть рюкзак, надеть предмет или продолжить маршрут.
- [ ] Решить, должен ли первый бой сразу давать уровень. Предпочтительный вариант — да, если это не ломает дальнейшую кривую опыта.
- [ ] Если выдаётся уровень, первый выбор перка должен заметно менять стиль игры, а не только увеличивать число.

### Критерии готовности этапа A

- Все три героя используют характерное умение уже в первой миссии.
- В первом раунде нет обязательной серии действий «переместиться → вне дальности → ждать».
- Новый игрок понимает различие ролей без чтения бестиария или полного журнала.
- Первая победа всегда даёт заметный источник силы.
- Повторный игрок может быстро пропустить обучение.
- `npm test` проходит.
- Первый бой вручную проверен минимум на desktop и 812×375.

## 6. Этап B — мобильный бой и базовая читаемость

Цель: сделать альбомный телефон полноценной платформой, а не уменьшенной desktop-версией.

### B1. Портретная ориентация не поддерживается

- [ ] Ввести единый полноэкранный экран «Поверните устройство» для всей игры в портретной ориентации.
- [ ] Не разрабатывать и не поддерживать отдельные portrait-компоновки меню, карты, боя, города, инвентаря и модальных окон.
- [ ] Не рендерить сжатый игровой интерфейс под экраном поворота.
- [ ] Сохранять текущее состояние игры и боя при смене ориентации.
- [ ] После возврата в landscape восстанавливать тот же экран без перезапуска или потери действия.

### B2. Сенсорные размеры

- [ ] Основные кнопки действий сделать высотой не менее 44 CSS px либо обеспечить эквивалентную невидимую touch-зону.
- [ ] Не использовать основной текст 8 px на мобильных экранах.
- [ ] Увеличить текущего героя, режим действия и ключевые значения HP/MP.
- [ ] Проверить расстояние между соседними действиями, чтобы исключить ошибочные нажатия.
- [ ] Не полагаться на hover для информации, необходимой на телефоне.

### B3. Компоновка боя

- [ ] Сохранить поле боя главным элементом экрана.
- [ ] Сделать панель героев компактной горизонтальной полосой.
- [ ] Показывать подробности только выбранного героя.
- [ ] Свернуть очередь ходов до портретов и ключевых маркеров угрозы.
- [ ] Сделать журнал скрытым по умолчанию на телефоне.
- [ ] Превратить правую колонку в компактную панель команд.
- [ ] Показывать только актуальные действия текущей фазы.
- [ ] Заблокированные будущие умения отображать менее заметно, чем доступные действия.

### B4. Целевые разрешения

Обязательная ручная проверка:

- [ ] 1280×720;
- [ ] 900×520;
- [ ] 812×375;
- [ ] 667×375;
- [ ] 375×667 — только корректный полноэкранный экран поворота вместо игрового UI.

### Критерии готовности этапа B

- На 812×375 и 667×375 все основные команды читаются без масштабирования браузера.
- По бою можно играть одним пальцем без частых ошибочных нажатий.
- Canvas не перекрывается панелями.
- Нет обязательной вертикальной прокрутки основного боевого HUD.
- Portrait никогда не показывает игровой UI и всегда предлагает повернуть устройство.
- В audit добавлены проверки ключевых mobile-классов и orientation gate.

## 7. Этап C — темп и управление боем

Цель: уменьшить время между решением и результатом, сохранив тактическую глубину.

### C1. Пустые действия

- [ ] Проанализировать среднее количество ходов до первого контакта по фиксированным seed.
- [ ] Сократить чрезмерно большие стартовые дистанции в обычных миссиях.
- [ ] Проверить плотность препятствий, чтобы путь не превращался в длинный обход без решений.
- [ ] Добавить единое действие завершения текущей фазы или хода, когда полезных действий больше нет.
- [ ] Не заставлять игрока отдельно подтверждать очевидное отсутствие доступных целей.

### C2. Скорость противников

- [ ] Добавить скорость анимаций ×1 и ×2.
- [ ] Запомнить выбор игрока.
- [ ] При ×2 ускорять перемещения и паузы, но не скрывать критические события:
  - смерть;
  - сильный статус;
  - взрыв;
  - призыв;
  - переход фазы босса.
- [ ] После длинной последовательности врагов быстро возвращать фокус к активному герою.

### C3. Предпросмотр действия

- [ ] Для обычной атаки показывать:
  - ожидаемый базовый урон;
  - снижение бронёй;
  - возможное добивание;
  - блокировку линией или дальностью;
  - возможный фланговый бонус.
- [ ] Для умения показывать область, стоимость, доступность и основной эффект до подтверждения.
- [ ] На телефоне открывать подробность первым касанием, подтверждать вторым или отдельной кнопкой.
- [ ] Не показывать гарантированный результат там, где есть случайность; использовать диапазон или шанс.

### C4. Приоритетные цели

- [ ] Сохранить существующие threat badges.
- [ ] Сделать badge понятным без бестиария: иконка + короткая подпись при выборе.
- [ ] Подсвечивать опасное действие врага заранее, когда правила позволяют прогноз.
- [ ] Не превращать подсказку в автоматическое решение за игрока.

### Критерии готовности этапа C

- Первый контакт в обычной миссии чаще всего происходит в первом или втором раунде.
- Игроку не требуется журнал, чтобы понять невозможность атаки.
- Скорость ×2 не ломает статусы, инициативу, звук и анимации.
- Предпросмотр совпадает с фактическим результатом в детерминированной части расчёта.

## 8. Этап D — визуальная и звуковая отдача

Цель: сделать каждое важное решение физически ощутимым.

### D1. Базовые атаки

- [ ] Добавить короткое движение или импульс атакующего.
- [ ] Добавить реакцию цели: flash, recoil или shake.
- [ ] Добавить короткий hit-stop только для сильных попаданий.
- [ ] Различать визуально ближнюю, дальнюю и магическую атаку.
- [ ] Не блокировать управление слишком длинными эффектами.

### D2. События боя

Для каждого события требуются:

- запись в журнале;
- компактный marker над юнитом или клеткой;
- визуальная реакция;
- звук, если он не перегружает сцену.

Список событий:

- [ ] критический удар;
- [ ] пробивание;
- [ ] блок;
- [ ] уклонение;
- [ ] отражение урона;
- [ ] отражение статуса;
- [ ] аура;
- [ ] лечение;
- [ ] восстановление маны;
- [ ] яд и горение;
- [ ] заморозка, оглушение, страх и сеть;
- [ ] воскрешение;
- [ ] фланг;
- [ ] снижение урона;
- [ ] взрыв;
- [ ] призыв;
- [ ] переход фазы босса.

### D3. Убийство и победа

- [ ] Усилить смерть приоритетной цели.
- [ ] Отличать смерть обычного врага, элиты и босса.
- [ ] После последнего врага дать короткую паузу перед экраном победы.
- [ ] Свести музыку, victory SFX и частицы в один короткий наградной момент.

### Критерии готовности этапа D

- Игрок способен назвать причину необычного результата без открытия журнала.
- Эффекты не закрывают HP, цели и доступные клетки.
- На ×2 основные события остаются различимыми.
- Все существующие proc-проверки продолжают проходить.

## 9. Этап E — карта и выбор маршрута

Цель: превратить перемещение по карте из разрешённого клика в осмысленный выбор риска.

### E1. Ближайшие варианты

- [ ] Сохранить существующую сетку и генерацию данных на первом проходе.
- [ ] В основном режиме карты визуально выделять только:
  - текущую точку;
  - 2–3 доступных варианта;
  - ближайшую важную цель;
  - направление босса.
- [ ] Остальные клетки оставлять вторичным фоном или доступными через полный обзор.
- [ ] Не показывать игроку большую массу одинаковых чёрных ячеек как основной контент.

### E2. Информация о точке

До входа показывать:

- [ ] тип точки;
- [ ] примерную угрозу;
- [ ] вероятный тип награды;
- [ ] особое условие или роль ключевого врага;
- [ ] связь с прогрессом к боссу.

Не раскрывать:

- точный случайный loot;
- полный состав обычной волны;
- результат события.

### E3. Маршруты

- [ ] Сформировать понятные категории:
  - безопасный путь;
  - путь за ресурсами;
  - рискованный путь с лучшей наградой.
- [ ] Гарантировать, что соседние варианты хотя бы периодически отличаются по смыслу.
- [ ] Не создавать ложный выбор из одинаковых миссий.
- [ ] Показать прогресс региона и расстояние до босса.

### E4. Карта и обучение

- [ ] После первой победы предложить два понятных маршрута.
- [ ] Один раз объяснить соотношение угрозы и награды.
- [ ] Сохранить управление кликом и клавиатурой через единый путь.

### Критерии готовности этапа E

- За несколько секунд игрок понимает различие доступных соседних точек.
- На карте есть видимая краткосрочная и региональная цель.
- Полный размер 12×8 не подавляет ближайшее решение.
- Offline-режим Wanderer/Arena продолжает работать.

## 10. Этап F — прогрессия, билды и инвентарь

Цель: каждый новый уровень или предмет должен менять следующее решение игрока.

### F1. Перки

- [ ] Проверить все 27 перков и разделить их на:
  - числовое усиление;
  - изменение правила;
  - новый боевой приём;

- [ ] Простые `+HP`, `+урон`, `+броня` использовать как поддержку билда, а не как главную награду ветки.
- [ ] Показывать краткое обещание ветки до выбора:
  - танк;
  - дуэлянт;
  - командир;
  - снайпер;
  - мобильный стрелок;
  - ловушки;
  - разрушение;
  - контроль;
  - мистика.
- [ ] Проверить, что описание каждого перка совпадает с фактическим кодом.
- [ ] Сделать эффект нового перка заметным уже в следующем бою.

### F2. Предлагаемые направления изменения ранних перков

Это направления дизайна, а не обязательные финальные формулировки:

- Гарет:
  - первая успешная защита прикрывает соседнего союзника;
  - удар щитом помечает или провоцирует цель;
  - плотный строй усиливает отряд.
- Алира:
  - смена позиции подготавливает усиленный выстрел;
  - добивание возвращает часть движения или действия;
  - ловушки создают контролируемую зону.
- Сэрис:
  - заклинание оставляет опасную клетку;
  - убийство контролируемой цели возвращает ману;
  - контроль одной цели усиливает следующий AoE.

Перед реализацией каждое изменение должно быть проверено на отсутствие дублирования с предметами и существующими флагами.

### F3. Предметы

- [ ] Сохранять сравнение `до → после`.
- [ ] Показывать не только сумму характеристик, но и изменяющие правила свойства.
- [ ] Объяснять конфликтующие модификаторы.
- [ ] Отдельно отмечать предмет, который лучше только для конкретного билда.
- [ ] Не делать `Надеть лучшее` единственным очевидно правильным способом игры.
- [ ] Гарантировать полезный первый предмет.

### F4. Пустой рюкзак

- [ ] Не оставлять большую пустую область без цели.
- [ ] Показать три слота и способы получить первый предмет.
- [ ] Добавить короткую подсказку о редкости и сравнении.
- [ ] После получения первого предмета убрать обучающий empty state.

### F5. Победа и уровень

- [ ] Показывать золото, опыт и loot в иерархии важности.
- [ ] При уровне показывать реальные изменения характеристик.
- [ ] При открытии умения дать отдельный сильный момент.
- [ ] При получении перка показать его эффект простым боевым примером.
- [ ] Не перегружать экран несколькими последовательными модальными окнами.

### Критерии готовности этапа F

- Первый выбор перка меняет стиль следующего боя.
- Игрок понимает, почему новый предмет лучше или хуже.
- Пустой инвентарь помогает поставить цель, а не выглядит незавершённым.
- После победы ясно, насколько сильнее стал отряд.
- Существующие сохранения корректно получают новые значения по умолчанию.

## 11. Этап G — баланс и генерация встреч

Цель: сделать рост сложности предсказуемым, но не монотонным внутри каждого боя.

### G1. Набор тестовых seed

- [ ] Расширить стандартный набор до 20–50 фиксированных seed.
- [ ] Сохранить небольшой быстрый набор для ежедневной проверки.
- [ ] Добавить отдельные наборы:
  - обычная сложность;
  - хардкор;
  - ранняя игра;
  - боссы;
  - потенциально опасные синергии.

### G2. Оценка синергии врагов

- [ ] Дополнить raw threat модификаторами составов:
  - лекарь + танк;
  - контролёр + убийца;
  - призыватель + защитник;
  - несколько взрывников;
  - несколько дальних врагов;
  - массовый яд или заморозка.
- [ ] Ограничить чрезмерные сочетания в обычных миссиях.
- [ ] Разрешать более жёсткие сочетания в явно обозначенных элитных точках.

### G3. Кривая регионов

Целевое направление:

- регион 2 по медианной сложности ощутимо выше региона 1;
- регион 3 заметно выше региона 2;
- обычная миссия не должна случайно имитировать босса;
- подземелье должно быть опаснее миссии того же региона;
- boss threat сравнивается с другими боссами и ручными прохождениями, а не напрямую с суммой обычной волны.

- [ ] Проверить текущий спад средней угрозы между регионами 1 и 2.
- [ ] Проверить высокие выбросы региона 2.
- [ ] Проверить подземелья региона 1 относительно региона 2.
- [ ] Провести ручные seed-прогоны до изменения золота или числа врагов.

### G4. Метрики ручного прогона

Для каждого тестового боя фиксировать:

- число раундов;
- время боя;
- потерянное HP;
- потраченные расходники;
- число пустых ходов;
- число использованных умений;
- смерть героя;
- основной источник сложности;
- ощущение справедливости.

### Критерии готовности этапа G

- Медианная кривая сложности растёт между регионами.
- Редкие пики находятся в заранее обозначенных опасных точках.
- Первый регион обучает ролям и не требует знания будущих умений.
- Хардкор усиливает давление, но не создаёт непроходимые стартовые seed.
- Отчёт обновлён до и после балансных изменений.

## 16. Первый рабочий блок

Первым изменением после утверждения этого плана должен быть единый FTUE-блок:

### Состав

- `PX-001`: стартовые умения;
- `PX-002`: первая миссия;
- минимальная часть `PX-003`: подсказки для трёх стартовых умений;
- `PX-004`: гарантированная награда.

### Причина объединения

Эти задачи формируют один пользовательский опыт. Если открыть умения, но оставить огромную дистанцию, проблема темпа сохранится. Если сократить дистанцию, но не дать умения, первая миссия всё равно не покажет индивидуальность героев. Если исправить бой без награды, игровой цикл оборвётся сразу после победы.

### Граница первого блока

Не включать:

- глобальную переделку всех миссий;
- полный redesign карты;
- полный mobile HUD;
- массовый ребаланс регионов;
- архитектурное разделение `index.html`.

### Проверка первого блока

- новая игра на обычной сложности;
- пропуск и прохождение tutorial;
- стартовое умение каждого героя;
- победа и гарантированная награда;
- продолжение старого сохранения;
- desktop 1280×720;
- mobile landscape 812×375;
- `npm test`;
- фиксированный seed smoke run.

Работа по этому плану считается завершённой, когда:

- первый бой сразу демонстрирует роли и умения трёх героев;

- автоматические и ручные проверки документированы и воспроизводимы.
